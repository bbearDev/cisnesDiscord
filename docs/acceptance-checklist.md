# Acceptance 검증 체크리스트

> **출처**: `.omc/specs/deep-interview-cisnes-discord-bot.md`(AC-1~AC-35, 원문 그대로 인용) ·
> `.omc/plans/cisnes-discord-implementation.md`(AC-P1~AC-P7, §5.1/§5.2/§5.6/§9/§12-b/§S9).
> **검증 방법 범례**: `unit` / `integration`(실 SQLite) / `e2e`(가짜 chzzkbot 하니스) / `observability`(지표 배선 확인) / `수동(사람)`(자동화 불가, 사람이 실제 방송·서버로 확인).
> **완료 정의(S9)**: AC-1~AC-35 전수 통과 + AC-P1~AC-P7 전부 통과 + 테스트 4계층 녹색 + 커버리지 임계(lines ≥ 90 / branches ≥ 85) 충족.

## 1. `auth-link` — 치지직 인증 연동 (AC-1 ~ AC-12)

- [ ] **AC-1** 신규 멤버가 서버에 입장하면 미인증 상태로 안내 채널만 보이며, 다른 채널은 보이지 않는다.
  **검증**: `수동(사람)` — 이것은 디스코드 서버 권한 설정(S0-9)의 결과이지 봇 코드가 만들거나 관측하는 것이 아니다. 자동 e2e 검증에서 명시적으로 제외되며, **S9 수동 항목 M-4** 로 올라간다.
- [ ] **AC-2** 안내 채널에서 인증을 시작하면 `state` 파라미터가 포함된 치지직 `account-interlock` URL이 해당 유저에게만 제공된다.
  **검증**: `e2e` — 인증 전 과정(state→인가→콜백→`users/me`→팔로워→역할+닉네임) 시나리오의 일부.
- [ ] **AC-3** `state` 는 발급 유저에 귀속되고 만료 시간이 있으며, 다른 유저가 같은 `state` 로 콜백해도 연동되지 않는다.
  **검증**: `e2e` — state 탈취 시나리오. 보조로 `unit`(`session` 만료/미지/nonce불일치 3갈래 구분).
- [ ] **AC-4** 콜백에서 Access Token을 받아 `GET /open/v1/users/me` 로 `channelId`/`channelName` 을 얻는다.
  **검증**: `e2e` — 인증 전 과정 시나리오의 일부.
- [ ] **AC-5** 해당 `channelId` 가 대상 채널 팔로워 목록에 **없으면** 입장을 거부하고, 유저에게 "팔로우 후 다시 시도" 안내를 보낸다.
  **검증**: `integration` — `follower-check` 3상태 매핑(`everSynced:true/isFollower:false`→`no` 등)과 **`unknown` 이 `no` 로 안 접히는지**를 실 SQLite 로 검증. 전체 흐름은 `e2e` 로도 커버.
- [ ] **AC-6** 팔로워로 확인되면 `인증됨` 역할을 부여하고 서버 닉네임을 `channelName` 으로 변경한다.
  **검증**: `e2e` — 인증 전 과정 시나리오의 일부.
- [ ] **AC-7** 이미 다른 디스코드 계정과 연동된 `channelId` 로 인증을 시도하면 **거부**하고, 기존 연동은 그대로 유지된다. DB에 `chzzk_channel_id` UNIQUE 제약이 있다.
  **검증**: `integration` — `link-repo` UNIQUE 거부 + 기존 행 무변화 확인. 보조로 `e2e`.
- [ ] **AC-8** AC-7 거부가 발생하면 운영 채널에 기록이 남는다.
  **검증**: `e2e` — 중복 연동 시나리오에서 운영 채널 기록 여부 확인(AC-7·8 쌍으로 검증).
- [ ] **AC-9** 운영자 전용 명령어로 연동을 해제할 수 있고, 해제 후에는 같은 치지직 계정으로 다른 디스코드 계정이 인증할 수 있다.
  **검증**: `integration` — 해제 후 재연동 시나리오. `/연동해제` 는 행을 **삭제**한다(soft-delete 금지).
- [ ] **AC-10** 인증에 쓰인 Access Token은 팔로워 확인 이후 보관하지 않는다(연동 자체는 `channelId` 로만 유지된다).
  **검증**: `unit` — `viewer-token.ts`(교환→`users/me`→메모리 폐기+`revoke` fire-and-forget, **DB 에 쓰지 않음**)를 코드 수준으로 고정. 보조로 `observability`(`viewer_token_revoke_failures` 로 잔여 권한 관측).
- [ ] **AC-11** 봇이 디스코드 닉네임을 변경할 수 없는 대상(서버 소유자, 상위 역할 보유자)일 때 인증은 성공 처리되고 닉네임 변경 실패만 운영 채널에 기록된다.
  **검증**: `e2e` — 닉네임 실패 격리 시나리오.
- [ ] **AC-12** 동일 유저가 인증을 중복 클릭해도 역할이 중복 부여되거나 오류가 노출되지 않는다(멱등).
  **검증**: `e2e` — 인증 멱등 시나리오.

## 2. `live-alert` — 치지직 라이브 시작 알림 (AC-13 ~ AC-19)

- [ ] **AC-13** chzzkbot이 보낸 방송 시작 웹훅을 수신하는 HTTP 엔드포인트가 있다.
  **검증**: `e2e` — 웹훅 토큰 4종(유효/무토큰/오토큰/`version:2`) 테스트가 엔드포인트 존재를 전제로 성립.
- [ ] **AC-14** 웹훅 요청은 공유 시크릿(또는 서명)으로 검증되며, 검증 실패 요청은 거부되고 기록된다.
  **검증**: `e2e` — 웹훅 토큰 4종(유효/무토큰/오토큰/`version:2`).
- [ ] **AC-15** 방송 시작 이벤트 수신 후 **1분 이내**에 지정 디스코드 채널에 공지가 게시된다.
  **검증**: `observability` — 판정 축은 **웹훅 수신 시각 기준** `live_webhook_to_post_ms`(§2 확정 해석; 목표 p95 ≤ 5초, 상한 30초 — 1분은 계약 한도이지 설계 목표가 아니다). 보조로 `e2e`(디스코드를 3초 지연시켜도 응답이 500ms 내). **`openedAt` 기준 총 지연은 별도 지표 `live_opened_to_post_ms` 로 관측만 하고 이 AC 의 합격 판정에는 쓰지 않는다.**
- [ ] **AC-16** 한 번의 방송에 대해 공지는 **정확히 1개**다. 방송 중 잠시 끊겼다 재연결되어 이벤트가 다시 와도 추가 공지가 나가지 않는다(`liveHash`/세션 식별자 기반 원장 조회).
  **검증**: `e2e` — 웹훅 재전송(같은 `liveHash` 5회 → 공지 1개). 보조로 `unit`(`live-hash` 결정론).
- [ ] **AC-17** 같은 웹훅이 재전송(retry)되어도 공지가 중복되지 않는다(멱등 키 기반).
  **검증**: `e2e` — 웹훅 재전송 시나리오(위 AC-16 과 같은 테스트가 겸한다).
- [ ] **AC-18** 봇 재시작 후에도 AC-16/AC-17의 중복 방지가 유지된다(원장이 DB에 영속화된다).
  **검증**: `integration` — 재시작 후 원장 복원. 보조로 `e2e`(재시작 관통 — 각 중복 방지 시나리오를 재기동 뒤 반복).
- [ ] **AC-19** 공지 게시에 실패하면(디스코드 장애 등) 재시도하고, 최종 실패 시 운영 채널에 기록한다. 알림 실패가 봇의 다른 기능을 멈추게 하지 않는다.
  **검증**: `e2e` — 디스코드 장애 격리(발송 전량 실패 중 인증 흐름 정상 완주). 보조로 `observability`(`discord_send_failures`).

## 3. `youtube-alert` — 유튜브 업로드 알림 (AC-20 ~ AC-26)

- [ ] **AC-20** 설정 파일의 각 유튜브 채널에 대해 WebSub 구독이 등록되고, 만료 전 자동 재구독된다.
  **검증**: `e2e` — WebSub 왕복 시나리오.
- [ ] **AC-21** 신규 업로드 발생 후 **1분 이내**에 지정 디스코드 채널에 공지가 게시된다.
  **검증**: `e2e` — WebSub 경로가 이 지연을 책임진다(RSS 폴백은 "누락 0"을 지키는 장치이지 "1분"을 지키는 장치가 아님을 §5.3 이 명시).
- [ ] **AC-22** 영상 종류(롱폼/쇼츠/예약공개/라이브 다시보기)와 무관하게 모두 공지된다.
  **검증**: `e2e` — 롱폼·쇼츠·예약공개·라이브 다시보기가 섞인 피드 1건을 주입해 4건 전부 공지되는지 확인(rev.8 픽스처, 종류별 분기·누락 0 고정).
- [ ] **AC-23** 같은 `videoId` 에 대해 공지는 **정확히 1개**다. WebSub은 영상 제목/설명 수정 시에도 알림을 보내므로, 이미 공지한 `videoId` 는 재공지하지 않는다.
  **검증**: `e2e` — WebSub 왕복 시나리오(AC-20·23 공용). 보조로 `unit`(`claim(kind='youtube_upload', eventKey=videoId)` — 제목/설명/`updated` 는 키에 넣지 않음을 고정).
- [ ] **AC-24** 봇 재시작 후에도 AC-23의 중복 방지가 유지된다.
  **검증**: `e2e` — 재시작 관통(AC-18/24 공용 시나리오).
- [ ] **AC-25** WebSub 푸시가 유실되는 경우에 대비해 RSS 폴백 폴링이 동작하며, 폴백으로 발견한 영상도 AC-23의 중복 방지를 통과한다.
  **검증**: `e2e` — RSS 폴백 시나리오.
- [ ] **AC-26** 최초 기동 시(원장이 비어 있을 때) 기존 과거 영상을 소급 공지하지 않는다.
  **검증**: `integration` — `seeded` 경로 격리(채널이 원장에 처음 등장할 때 피드 전 항목을 `seeded=1` 로 선점만 하고 발송하지 않음, 스키마 CHECK 가 실제로 INSERT 를 거부하는지 확인). 보조로 `e2e`(콜드 스타트).

## 4. `infra` — 운영 기반 (AC-27 ~ AC-35)

- [ ] **AC-27** 연동 매핑·알림 원장·구독 상태가 SQLite에 저장되고 재시작 후 그대로 복원된다.
  **검증**: `integration` — 재시작 후 원장 복원.
- [ ] **AC-28** 스키마 변경은 chzzkbot과 동일한 번호순 마이그레이션 러너로 적용되며, 재실행해도 안전하다.
  **검증**: `integration` — `migrate` 멱등·중복거부·롤백.
- [ ] **AC-29** 다운타임이 **기준 시간(기본 6시간)** 이하이면 밀린 유튜브 업로드를 순서대로 전부 공지하고, 복구 시점에 방송이 진행 중이면 방송 공지를 1회 게시한다.
  **검증**: `e2e` — 다운타임 복구 3h/7h 분기(`live:true,confirmed:true` → 1건, `live:false` → 0건).
- [ ] **AC-30** 다운타임이 기준 시간을 **초과**하면 밀린 알림을 모두 생략하고, 운영 채널에 "‹기간› 동안 중단됨" 기록만 남긴다.
  **검증**: `e2e` — 다운타임 7h 복구 분기. **단, "밀린 알림 생략"은 지나간 이벤트(유튜브 밀린 업로드)에만 적용되고, 복구 시점에 진행 중인 방송은 6시간을 넘겨도 1회 공지한다**(§5.1 경계 2 — 라이브 경로에는 `seeded` 선점을 하지 않는다).
- [ ] **AC-31** 이미 종료된 방송에 대해서는 복구 후에도 "방송 시작" 공지를 게시하지 않는다.
  **검증**: `e2e` — 종료 판정(`!live+status:'running'` → 종료, `!live+status:'starting'` → 판정 안 함). 3상태 판정식(`announce`/`ended`/`unknown`)이 근거이며, `unknown` 을 `ended` 로 접지 않는 것이 조건.
- [ ] **AC-32** 디스코드 봇 토큰, 치지직 Client ID/Secret, 웹훅 시크릿이 저장소에 커밋되지 않으며 `.env`/설정으로 주입된다. 로그에 마스킹되어 출력된다.
  **검증**: `observability` — 전 로그 캡처해 토큰·웹훅 URL·`LIVE_API_TOKEN` 형태 0건 확인. 보조로 `unit`(`redact` 함수 — 봇 토큰·웹훅 URL·`LIVE_API_TOKEN` 형태 고정).
- [ ] **AC-33** systemd 유닛으로 상시 구동되고, 프로세스가 죽으면 자동 재시작된다.
  **검증**: `수동(사람)` — 실배포 systemd(user 유닛, `Restart=always`, `RestartPreventExitStatus=70 78`)에서 `kill -9` 후 10초 내 재기동 + 락 인수, `enable-linger` 미설정 시 경고를 실제로 확인해야 한다(**S9 M-3** 과 함께 검증). 보조로 `e2e`(EADDRINUSE — 포트 선점 후 기동 시 30초 백오프 재시도 후 exit 78, 점유 해제 시 정상 기동 — 이 로직 자체는 자동화 가능하나 systemd 의 실제 재시작 억제 동작은 사람이 확인한다).
- [ ] **AC-34** 헬스체크(하트비트)가 있고, 일정 시간 갱신되지 않으면 운영 채널에 알림이 간다.
  **검증**: `수동(사람)` — 봇 바깥의 워치독 타이머(`OnCalendar=hourly`)가 실제로 디스코드에 알림을 보내는지, 하트비트 91분 전 조작 시 알림 1건이 오는지 실배포에서 확인한다. 보조로 `observability`(`GET /healthz` 하트비트 나이 + DB 버전 노출 확인).
- [ ] **AC-35** 단일 인스턴스 가드가 있어 같은 DB에 두 프로세스가 동시에 붙지 않는다.
  **검증**: `integration` — `single-instance` 락·인수(죽은 PID 의 락을 인수하는지 포함).

## 5. 계획 추가 수용 기준 (AC-P1 ~ AC-P7)

> 스펙의 AC-1~35 와 번호 공간이 다르다(AC-36 처럼 이어 붙이지 않는다). 계획이 "남는 누락"(§12-b)을 **관측 가능**하게 만들기 위해 추가한 경보·지표 기준이다.

- [ ] **AC-P1** `live === true && confirmed === false` 상태가 `live.confirmedStuckMin`(기본 **5분**) 이상 연속 지속되면 운영 채널에 경보한다. (정상 창은 대기 채팅 14초 + 스캔 수십 초이므로 5분이면 오탐 없음. 경보 문구에 지속 시간 + chzzkbot 로그 확인 명령을 싣는다.)
  **검증**: `e2e` — `confirmed` 고착 경보(5분 지속 → 경보 1건, 공지 0개). 보조로 `unit`(`stuck-watch` 경계: 4:59→무경보/5:00→경보), `observability`(`live_unconfirmed_duration_sec`).
- [ ] **AC-P2** `unknown` 이 `live.pollFailThresholdCount`(기본 **5회** 연속, 기본 주기 3분 기준 15분) 관측되면 운영 채널에 경보한다.
  **검증**: `e2e` — 조회 API 를 연결 실패로 고정 → 5회째에 경보 1건, 그동안 공지 0개. 보조로 `observability`(`live_api_unknown_streak` — `/api/live` 가 유일한 아웃바운드라 이 값이 곧 통합 건강도).
- [ ] **AC-P3** 부하가 걸려도 (a) 디스코드 게이트웨이 재연결이 늘지 않고 (b) 아웃바운드 in-flight 가 `http.maxConcurrent`(기본 **8**) 를 넘지 않으며 (c) 각 인증이 OAuth 왕복 예산(10초) 안에 종결된다.
  **검증**: `e2e` — FM1 부하 격리(동시 인증 10명 + 가짜 상류 300ms 지연 → 게이트웨이 재연결 0건 / in-flight ≤ 8 / 왕복 예산 내 종결). 관측 수단은 `fake-discord.ts` 의 `reconnectCount` 로 못 박는다. 보조로 `observability`(`discord_gateway_reconnects`).
- [ ] **AC-P4** RSS 폴이 채널 단위로 `youtube.rssFailThresholdCount`(기본 **5회**) 연속 실패하면 운영 채널에 경보한다. 중간에 1회라도 성공하면 카운터를 리셋한다.
  **검증**: `e2e` — RSS 5회 연속 실패 → 경보 1건, 4회에서는 0건, 중간 성공 시 카운터 리셋. 보조로 `unit`(`stuck-watch` 경계), `observability`(`youtube_rss_fail_streak{channel}`).
- [ ] **AC-P5** WebSub 푸시의 `X-Hub-Signature` 검증 실패는 계약대로 조용히 202 로 답하되, `websub_signature_failures{channel}` 지표를 반드시 증가시킨다.
  **검증**: `e2e` — 잘못된 시크릿으로 서명한 푸시 → 202 응답 + 공지 0개 + 지표 증가 1. 보조로 `observability`(`websub_signature_failures{channel}` — "시크릿 불일치"와 "허브가 안 보냄"을 구분하는 유일한 축).
- [ ] **AC-P6** 폴링이 `announce` 를 냈고, 그로부터 `live.webhookSilenceGraceMin`(기본 **10분** = 재시도 창 7분 + 여유 3분) 이 지난 뒤에도 같은 `liveHash` 에 대해 웹훅을 받은 기록이 원장에 없으면 운영 채널에 1건 기록한다.
  **검증**: `e2e` — 웹훅 침묵(유예창 경과 후 공지 1건 + 운영 채널 기록 1건, 웹훅으로 받은 방송은 기록 0건) + 오경보 부재(폴링이 `announce` claim 후 5분 뒤 chzzkbot 재시도 웹훅 도착 → 공지 1건, **경보 0건** — 정상 시퀀스에서 오경보가 안 남을 확인). 보조로 `observability`(`live_webhook_silence_sec`).
- [ ] **AC-P7** 설정 키 `youtube.leaseWarnRatio`(기본 0.2) · `youtube.renewFailThresholdCount`(기본 3). WebSub 구독 잔여가 리스의 20% 미만이거나 `last_renew_error` 가 연속 3회 쌓이면 운영 채널에 경보한다. 기동 시 모든 구독의 잔여를 로그 한 줄로 남긴다.
  **검증**: `e2e` — 리스 잔여 15%로 조작 → 경보 1건 / 25%에서는 0건. 갱신 3회 연속 실패 → 경보 1건, 2회에서는 0건. 보조로 `observability`(`websub_lease_ratio{channel}` / `websub_renew_fail_streak{channel}`).

## 6. 수동 재현 4건 (M-1 ~ M-4) — 자동화 불가, 사람이 실제 방송·서버로 확인

> S9 완료 정의의 일부다. M-1 을 건너뛰면 "누락 0" 의 실제 범위를 아무도 확인하지 않은 채 출시된다. 두 절차(M-1/M-2) 는 `docs/runbook-ops.md` 에도 싣는다.

- [ ] **M-1** — **무채팅 방송 누락 재현**
  **절차**: 대상 채널을 켜고 아무도 채팅하지 않은 채 10분 대기.
  **기대**: 공지 0건. `/api/live` 는 `live:false`. **§12-b 가 문서화한 "남는 누락" 그대로임을 확인** — 이것을 버그로 처리하지 않는다.
  **관련**: Goal "누락 0"(조건부), §12-b.

- [ ] **M-2** — **S0-13 절차 유효성**
  **절차**: M-1 상태에서 스트리머가 채팅 한 줄을 입력한다.
  **기대**: 세션이 열리고, `confirmed` 도달 후 공지 1건. `detected_via='webhook'`.
  **관련**: AC-13, AC-15, AC-16, S0-13.

- [ ] **M-3** — **EADDRINUSE 플래핑 부재**
  **절차**: 다른 프로세스로 포트를 점유한 채 `systemctl start` 실행.
  **기대**: 30초 백오프 후 **exit 78 → systemd 가 재시작하지 않는다**(`systemctl status` 가 `failed`). 로그에 `ss -ltnp` 안내. **무한 재시작이 없어야 한다.**
  **관련**: AC-33, §5.4.

- [ ] **M-4** — **AC-1 채널 가시성**
  **절차**: 새 계정으로 서버 입장 후 채널 목록 확인.
  **기대**: 안내 채널만 보이고 나머지는 보이지 않는다. 인증 후 전부 보인다. **S0-9 설정의 결과이므로 코드·테스트가 아니라 사람이 눈으로 확인한다.**
  **관련**: AC-1, S0-9.

## ★ 이 체크리스트가 전제하는 것 — 서명 전에 읽는다

AC-1~35 · AC-P1~P7 은 **단일 디스코드 길드 배포**를 전제로 판정한다.

| 항목 | 상태 | 근거 |

| **단일 길드 전제** | ⚠️ 하드 제약 | `verification_sessions` 에 `guild_id` 컬럼이 없다(계획 §8). 콜백은 `guild_config` 에서 길드를 해석하고, 없으면 **인증을 실패시킨다**(추측하지 않는다). 다길드는 마이그레이션 `002` 선행 |
