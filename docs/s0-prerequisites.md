## 5. ★★ 가장 어려운 관문 1 — S0-5: HTTPS 종단이 실질적으로 존재하지 않는다

**실측 결과 (rev.5, 실배포 확인)**

| 확인한 것 | 결과 |
|---|---|
| nginx · caddy · apache2 · traefik | **전부 inactive** |
| 80 / 443 리스닝 | **없음** |
| cloudflared · tailscale · frp · ngrok(터널) | **없음** |
| `CHZZK_REDIRECT_URI` | `https://<HOST>/oauth/chzzk/bot-callback` — 포트 없음(=443). **지금 도달 불가능한 주소다** |

**왜 S0-3 못지않은 블로커인가**
- **S4 (인증)**: 치지직이 사용자 브라우저를 `redirectUri` 로 돌려보낸다. 종단이 없으면 **OAuth 콜백이 아예 도달하지 못해 인증 기능 전체가 동작 불가**다.
- **S6 (유튜브)**: WebSub 허브가 공개 HTTPS 로 우리에게 푸시한다. 종단이 없으면 구독 검증(`hub.challenge`)부터 실패해 **AC-20 이 성립하지 않는다.**
- 반면 **S5 (라이브 알림)는 막히지 않는다** — 웹훅 수신도 `/api/live` 폴링도 둘 다 루프백(`127.0.0.1:8080`↔`127.0.0.1:8081`)이라 프록시가 필요 없다. **S5 를 먼저 완주할 수 있다.**

**공개해야 하는 경로는 셋뿐이고, 경로를 바꾸지 않고 그대로 넘긴다** (앱이 서비스하는 경로 그 자체다):
```
https://<HOST>/oauth/start              →  <앱>:8081/oauth/start
https://<HOST>/oauth/callback           →  <앱>:8081/oauth/callback
https://<HOST>/websub?channel=<채널ID>   →  <앱>:8081/websub   (질의문자열 그대로)
```
> ★★ rewrite · strip_prefix 를 쓰지 않는다. WebSub 콜백 주소는 봇이 `publicBaseUrl + /websub`
> 로 만들어 **허브에 직접 등록**하므로, 프록시가 다른 모양을 기대하면 구독이 영영 확정되지
> 않는다 (`websub_subscriptions.lease_seconds` 가 빈 채로 남는다).
> `<앱>` 은 프록시와 같은 호스트면 `127.0.0.1`, 다른 호스트면 앱 호스트의 LAN 주소다.

chzzkbot 웹훅(→8081)과 우리 폴링(→8080)은 루프백이므로 프록시 대상이 아니다.

> ⚠️ 위 콜백 경로가 **chzzkbot 의 기존 `CHZZK_REDIRECT_URI` 경로와 겹치면 안 된다**(S0-2). 콜백은 `code`/`state` 만 받으므로 어느 앱의 코드인지 구분할 수 없다.

**프록시 선택은 사람이 결정한다 (§11 D-7)**: nginx 와 caddy 는 **인증서 자동화 유무**에서 갈린다 — caddy 는 ACME 내장이라 설정 한 줄로 발급·갱신이 자동이고, nginx 는 certbot 을 따로 붙여야 한다. 경로가 2개뿐이라 **caddy 를 권고**하지만, 운영자가 이미 nginx 에 익숙하면 그 선택이 낫다 — **유지보수를 실제로 할 사람의 취향이 비용을 정한다.** 계획은 어느 쪽도 강제하지 않고 두 가지 예시 conf 를 함께 제공한다.

배포 런북에는 반드시 **콜백·WebSub 경로에 IP 리밋(분당 60/IP)이 실제로 걸려 있는지** 확인하는 항목을 넣는다(§5.6.2 — 앱 코드가 아니라 프록시 설정이라 코드로는 검증되지 않는다). 단, `/websub/:chId` 허브 경로는 IP 리밋 대상에서 빼거나 넉넉히 잡는다(허브 IP 가 소수에 몰려 있어 리밋을 걸면 정상 푸시가 조용히 드롭될 수 있다).

## 6. ★★ 가장 어려운 관문 2 — S0-15: chzzkbot 팔로워 조회 API, **대체 경로가 없다**

**작업의 실체 — 없는 것을 만드는 게 아니라 있는 것을 노출하는 일이다.** chzzkbot 은 이미 팔로워 동기화 인프라를 갖고 있다(`ever_synced`, `cached_at` 등). S0-15 는 그 조회 결과를 cisnesDiscord 가 물을 수 있는 **단건 판정 엔드포인트** 하나로 얇게 노출하는 작업이다.

**계약 요구 (§5.2 R1~R5) — 요약**

| 요구 | 내용 | 근거 |
|---|---|---|
| **R1** 단건 판정 | `GET /api/followers/:channelId/:viewerChannelId` — **목록이 아니라 단건**이어야 한다. 목록을 받으면 우리가 다시 전량 페이징을 다뤄야 해서 이번 위임 결정의 이득이 사라진다 | 기존 스키마 인덱스 조회 1건이면 충분 |
| **R2** `everSynced` | 응답에 반드시 포함. `everSynced:false` 는 **"미팔로우"가 아니라 "아직 모른다"** — 이 둘이 안 갈리면 chzzkbot 기동 직후 전원이 거부된다 | ✅ `follower_sync_state.ever_synced` 컬럼 이미 존재 |
| **R3** `cachedAt` | **반드시 `followers.cached_at`(데이터 세대 시각)에서 와야 한다.** `follower_sync_state.last_full_sync_at` 을 쓰면 동기화 실패 시 이 값이 NULL 로 덮여 **나이 정보 자체가 사라진다** — 계약이 조용히 무력화된다 | ✅ 소스 확인됨(`follower-repo.ts:126`) — 아래 검사 절차로 실배포에서 직접 검증 가능 |
| **R3-b** `lastError` | 권장(필수는 아님) — 있으면 장애 원인 구분이 빨라진다 | ✅ `follower_sync_state.last_error` 이미 존재 |
| **R4** 토큰 | `LIVE_API_TOKEN` 관례 재사용, 헤더 `x-chzzkbot-token`, 16자 이상 | ✅ 관례 재사용 |
| **R5** 채널 경계 | 토큰 하나가 등록된 모든 채널(현재 `시스네`+`아이곰` 2채널)을 열므로, **cisnesDiscord 쪽이 `channelId` 로 다시 걸러야 한다** | 상류 변경 불필요 — 우리 쪽 재필터 |
| **R6** ★★ 방송 밖 갱신 | 상류의 팔로워 캐시 주기 갱신이 **방송 중이 아닐 때도** 돌아야 한다. 이 API 의 소비자(입장 인증)는 방송과 무관하게 오고, 우리 신선도 게이트는 스냅샷이 `follower.staleAfterMin`(150분)보다 오래되면 판정을 유보한다 — 방송 밖에서 캐시가 멈추면 **방송이 없는 시간 내내 아무도 서버에 못 들어온다** | ⚠️ **2026-09-12 실배포에서 깨졌던 조항.** chzzkbot 이 `activeSessionId` 가 없으면 주기 갱신을 건너뛰고 있었고(`!팔로우` 만 읽는다는 전제), 새벽 방송 뒤 낮의 인증 5건이 전부 `stale` 로 유보됐다. **`bbearDev/chzzkbot#9` 이상**이어야 한다. 아래 검사 절차 참조 |

구현 순서(계획 권고): ① 라우트 + 토큰 검증(기존 `live-api.ts` 패턴 그대로) → ② 조회 + 응답 조립 → ③ 설정 `liveEvents.followerApi.enabled` → ④ 기동 로그.

### ★ R3 준수 검사 절차 — **오늘 실배포 `bot.db` 로 검증 가능, 새 코드를 기다릴 필요 없다**

R3(`cachedAt` 이 `followers.cached_at` 에서 온다)이 계약에서 결과가 가장 큰 조항인데, 상류가 어느 컬럼을 실었는지 **정상 동작 중에는 두 값이 비슷해 눈으로 구분되지 않는다.** 차이는 오직 동기화가 실패했을 때만 드러난다.

**절차**:
1. 상류 동기화를 **1회 강제 실패**시킨다 (예: 일시적으로 잘못된 토큰을 넣거나 네트워크를 차단).
2. `follower_sync_state.last_full_sync_at` 이 **NULL 이 되는지** 확인한다.
3. 그 상태에서 `GET /api/followers/…` 를 호출해 응답의 **`cachedAt` 이 여전히 값을 갖는지** 확인한다.

**판정**: `cachedAt` 이 **null 이 되면 R3 위반**이다 — 상류가 `last_full_sync_at` 을 실은 것이고, 그러면 우리 쪽 신선도 게이트가 나이를 잃어 무력해진다(우리 쪽은 판정표 0-b 규칙으로 `unknown` 처리해 방어하지만, 그건 방어이지 계약 충족이 아니다).

### ★ R6 준수 검사 절차 — 방송이 끝나고 2시간 뒤에 본다

R6(방송 밖 갱신)은 **방송 중에는 절대 드러나지 않는다** — 세션이 열리면 상류가 즉시 당겨 받고 주기도 돌기 때문이다. 깨져 있어도 방송 중 인증은 멀쩡하고, 방송이 끝나고 `staleAfterMin`(150분)이 지난 뒤의 인증부터 조용히 전부 유보된다.

**절차** (방송 종료 후 2시간 이상 지난 시점에):
```bash
# 상류 스냅샷 나이(분). 정상이면 130분 아래다 (안전장치 60분 + 채널별 지터 0~60분 + 10분 틱)
sqlite3 ~/git/chzzkbot/data/bot.db \
  "SELECT channel_id, last_full_sync_at,
          CAST((julianday('now') - julianday(last_full_sync_at)) * 1440 AS INTEGER) AS age_min
     FROM follower_sync_state;"
# 우리 쪽에서 본 것 — reason='stale' 이 이어지면 같은 사실이다
grep -h '팔로워 판정 보류' data/logs/cisnes.$(date +%F).*.log | tail -5
```

**판정**: 방송 밖에서 `age_min` 이 **150 을 넘으면 R6 위반**이다. 조치는 chzzkbot 을 `#9` 이상으로 올리고 재기동. 그 뒤 첫 주기(`followerCacheMin` 10분)부터 수 조회가 돌고 1~2시간 안에 전수가 한 번 돈다.

**상류 갱신의 실제 모양 — `cachedAt` 은 정상이어도 최대 2시간 남짓(≈ 130분) 묵는다.** 상류는 주기마다 팔로워 **수**를 1회 물어보고, 목록 전체를 다시 받는 것(= `cachedAt` 이 움직이는 것)은 수가 달라졌을 때(최소 30분 간격)와 안전장치 전수뿐이다. 안전장치 간격은 **60분이 아니라 60분 + 채널마다 고정된 지터(0~60분)** 이고 판정이 10분 틱에서만 일어난다 — 실측 시스네 62.6분, 아이곰 105.9분(`chzzkbot#9` 리뷰). 그래서 `staleAfterMin` 150분은 그 상한 위에 **20~35분** 여유를 두고 있는 값이고, **이 아래로(90분·2시간 등) 내리면 정상 상태가 `stale` 로 읽힌다.** "상류는 1시간마다 갱신" 이라는 문장을 어디서 보든 믿지 말 것 — 이번 사고가 정확히 그런 한 줄에서 시작됐다. AD-2 재조회(`cachedAt + 10분 + ε`)는 방송 밖에서는 이미 지난 시각일 수 있어 즉시 한 번 더 묻는 것으로 끝난다 — 그때 새 팔로우가 아직 안 잡혔으면 사용자가 잠시 뒤(≤ 30분) 다시 눌러야 한다.

**미완료 시 폴백 — 없다. 이것이 S0-15 의 성질이다.**
- S4 의 팔로워 검증은 **이 API 없이는 대체 경로가 없다.** cisnesDiscord 는 `channels/followers` 를 직접 호출하지 않기로 결정했고(린트로 금지), 스트리머 토큰도 들지 않는다.
- "S5 를 먼저 완주" 완화는 이 위험에 조준되지 않는다 — 순서를 바꿔도 막히는 것은 **S4(진입 기능)** 이다. **S0-15 없이는 사람이 서버에 들어올 수 없다.**
- 개발 중 우회: `fake-chzzkbot.ts` 가 계약대로 응답하므로 테스트는 진행 가능하다. 막히는 것은 **실환경 검증과 출시**다.
- 운영 중 상류 장애 시의 완화는 **AD-3(수동 승인 — 운영자가 사람 근거로 잠정 승인, 상류 복구 후 재검증)** 이다.

> §11 **D-6**(팔로워 신선도의 수용선): 상류 `followerCacheMin` 10분을 그대로 수용하기로 확정됐다(강제 갱신 트리거를 상류에 요청하는 방안은 채택하지 않음 — 민원이 실제로 생기면 그때 요청한다).
>
> ★ 2026-09-12 에 그 민원이 실제로 생겼고, 원인은 "10분" 이 아니라 **R6(방송 밖 갱신 없음)** 이었다. 요청 시 강제 갱신은 그때 다시 검토했지만 채택하지 않았다 — 상류가 수가 같으면 `cachedAt` 을 안 움직여 그대로는 동작하지 않고, 전수는 십수 초라 요청 안에서 못 기다리며, 그래서 첫 인증이 반드시 한 번 실패한다. 방송 밖 주기 갱신(`chzzkbot#9`)이 그 세 문제를 한 줄로 없앤다.

## 7. S0-12b 순서 제약 — 웹훅 URL 은 **cisnesDiscord 수신부가 뜬 다음에만** 채운다

> **① `WEB_PORT` 는 지금 넣어도 무해하다.** 웹 서버가 떠서 `/api/live` 조회만 열린다 — 아직 폴링하지 않아도 부작용이 없다(이미 완료됨).
>
> **② 웹훅 URL 은 cisnesDiscord 수신 엔드포인트(8081)가 실제로 뜬 뒤에 채운다.** 먼저 채우면 그 사이에 켜진 방송이 **8회 실패 후 포기**되고(재시도 창 7분 — `maxAttempts:8` × `retryIntervalMin:1`, 즉시 1회+재시도 7회), 그 행은 이후 조회에서 다시 주지 않아 **소급되지 않는다.** 빈 값으로 두면 애초에 발송권을 집지 않으므로 잃는 것이 없다 — 나중에 채우면 그때부터의 방송이 정상적으로 나간다.
>
> **완화**: 순서를 어겨 놓친 방송이라도 **복구 시점에 여전히 진행 중이면** `/api/live` 폴링이 메운다. 끝난 방송은 AC-31 대로 공지하지 않는다.

이 관계를 의존 그래프로 표시하면: **S3(cisnesDiscord 수신 엔드포인트가 8081 에서 실제로 뜨는 것) → S0-12b(웹훅 URL 주석 해제)**. S0-12b 를 S3 보다 먼저 하지 않는다.

```
S0 (사람 · 상시 병렬) ──────────────────────────────────────────────
   └ S0-3  (유저 정보 조회 Scope)  ─→ S4 게이트 (신청 대상이면, S1-E2 확인)
   └ S0-12 (chzzkbot 외부연동) — ①WEB_PORT ✅ 완료 / ②웹훅 URL = S0-12b
   │      ★ S3 (수신부 8081 기동) ──→ S0-12b (주석 해제) ──→ S5 완주
   │      ※ ②를 S3 보다 먼저 채우면 그 사이 방송이 8회 실패 후 소급 불가
   └ S0-5  (HTTPS 종단·프록시) ★ ─→ S4 · S6 게이트
   └ S0-15 (chzzkbot 팔로워 API) ★ ─→ S4 팔로워 검증 게이트
       ※ S5 는 루프백이라 S0-5 없이 완주 가능 — 먼저 돌린다
```

## 8. S0-16 / §5.2-c — `CHZZK_CLIENT_ID` 는 반드시 chzzkbot 것과 달라야 한다

**같으면 벌어지는 일 (연쇄, 계획이 확정한 사실들의 조합)**:
```
전제 1  cisnesDiscord 는 시청자 토큰을 쓰고 나서 revoke 한다 (보관 금지, AC-10)
전제 2  revoke 는 "clientId 와 user 가 동일한 모든 Token"을 제거한다 (치지직 문서)
전제 3  스트리머도 자기 디스코드 서버의 멤버다 — 언젠가 /인증 을 누른다
전제 4  chzzkbot 은 그 스트리머의 토큰으로 팔로워 캐시를 갱신한다

   우리 앱의 clientId == chzzkbot 의 clientId  이면
      스트리머가 /인증 → 우리가 시청자 토큰 획득 → revoke 호출
      → clientId 같고 user 같음 → chzzkbot 의 스트리머 토큰이 함께 제거된다
      → chzzkbot 팔로워 캐시 갱신 정지 → 우리 팔로워 검증이 전원 정지
      → 복구에는 스트리머의 브라우저 재인가가 필요하다
```

**즉 viewer(시청자) 한 명의 인증이 chzzkbot 의 스트리머 토큰을 폐기시켜, 그 순간부터 아무도 팔로워 검증을 통과하지 못하게(follower verification 전면 정지) 된다.** 되돌릴 수 없고, 복구에는 스트리머 본인이 브라우저로 재인가해야 한다.

**확인 절차 (S0-1 에서 새 앱을 등록하는 그 자리에서 함께 수행)**:
1. 개발자센터에서 **새 앱을 등록**한다. 기존 chzzkbot 앱을 고르지 않는다.
2. 발급된 `clientId` 를 우리 `.env` 의 `CHZZK_CLIENT_ID` 에 넣는다.
3. **chzzkbot `.env` 의 `CHZZK_CLIENT_ID` 와 눈으로 대조해 다른지 확인한다.**
4. 기동 로그에 찍힌 우리 `clientId` 로 3번을 한 번 더 확인한다.

**왜 사람이 하는가**: cisnesDiscord 는 chzzkbot 의 `.env` 를 읽지 않는다(두 프로세스는 웹훅/HTTP 로만 결합한다는 결합 규칙). 따라서 **기계로 자동 대조할 수단이 없다.** 이것은 실측이 아니라 설정 불변식이므로 S1 스파이크가 아니라 S0 사람 확인이 맞는 자리다.

> 기계 방어(코드 쪽 안전장치)도 함께 들어간다 — 보호 채널(`live.channelId` + chzzkbot 이 서빙하는 채널 전체)에 대해서는 revoke 를 건너뛰는 로직(AD-1)이 있다. **그러나 이것이 S0-16 을 대체하지 않는다** — 기계 방어는 `clientId` 가 같을 때의 *피해*를 줄이고, S0-16 은 `clientId` 가 같아지는 것 *자체*를 막는다. 서로 다른 층이다. 또한 **배포 런북에서 매 배포마다 재확인**해야 한다 — 앱 재등록·시크릿 로테이션·호스트 이전마다 이 문제가 재발할 수 있고, 깨져도 겉으로는 몇 주간 아무 일도 없어 보이기 때문이다.
